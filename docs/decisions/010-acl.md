# ADR 010 — Audience ACLs: derived from the path, enforced at the answer

**Status:** accepted · 2026-07-13

## Context

Everything ingested was visible to every client: per-source scoping is all-or-nothing over the
corpus. For a real company that is the #1 adoption blocker — payroll, board minutes and client
financials cannot share one visibility scope with the product roadmap.

## Decision

Audience labels with the same shape as entity resolution — **who may see a document is a
property of where it lives**, mapped by ordered config, never by an LLM:

- **Resolution (pure code)**: a JSON of ordered rules (`path_prefix` / `path_contains` / `unit` /
  `entity_kind` → audiences; first match wins; explicit default). The resolved list lands on the
  page (`acl: [...]`) and on a view as the **intersection** of its members' audiences
  (`kernel.acl.view_acl`) — a rollup must never widen access to what it summarizes. A malformed
  config errors loudly: silently-open is the one failure mode an access-control file must not
  have. No config = open corpus (no `acl` field).
- **Enforcement (pure code, at the answer)**: one visibility rule everywhere — no ACL → visible
  to all; unrestricted client → sees everything; else intersect. Search drops out-of-scope pages
  (it does not annotate them: an invisible page simply isn't there), `read_page` denies, and even
  entity *existence* is scoped. `server.acl.visible()` is the one place read access is decided
  — `kernel.acl` resolves and composes labels, the server enforces them — and every reader of the
  index either names that predicate (or `kernel.acl.visible_to_view`, its view-side sibling) or is
  a listed, tested exception.

Audiences were originally a **deployment property**: one server instance = one ACL scope,
multi-tenant = one instance per scope. That is still how a local stdio process works
(`--identity`), and [ADR 013](./013-http-transport-and-token-auth.md) added the per-request half
beside it — a bearer token resolves to an email, the email to audiences — without changing the
enforcement primitive at all. The seam this ADR drew is exactly where the second stage slotted in.

## Consequences

- The eval proves the product behavior: the same question is answered for the unrestricted
  identity and **refused** for one scoped to audiences that do not include the page's, with the
  restricted page absent from its search results and no existence leak in the refusal.
- A view cannot leak what its members restrict (intersection, then the same `visible()` check).
- Deliberate limitation, documented: this maps *conventions* to audiences. Mirroring live
  per-file Drive permissions is a connector concern — the fetch path already persists whatever
  metadata Drive returns, and would feed the same `acl` field.

Audience labels also landed on every row of a fact store, which inherited its document's
audience. That store was removed later ([ADR 026](./026-the-purge.md)); inheritance is not a rule
anything still applies, because pages are now the only thing that carries a figure.

## Alternatives rejected

- **Per-request multi-tenant OAuth in the answer server** — real identity-provider integration
  belongs in front of it; a static per-instance scope is honest, testable and composable with any
  ingress, and per-user bearer tokens later filled the gap without touching enforcement.
- **LLM-assigned sensitivity labels** — access control must be deterministic and auditable.
- **Filtering at ingestion** (separate corpora per audience) — N corpora to keep consistent;
  labels + one enforcement point beat data duplication.
